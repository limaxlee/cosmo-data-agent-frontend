# Change A: logout always lands on `/chat/new`

**Files changed:**

| File | Change |
|---|---|
| `src/components/user-gate.tsx` | One effect: when there is no user, replace the URL with `/chat/new`. |

No other file changes. The logout button in the sidebar and the expiry timer in
the user provider are untouched; both already end in `clearUserId()`, and the
gate reacts to the result.

---

## A1. Behavior

### Before

`UserGate` wraps every page from the root layout. When `userId` becomes `null`
it swaps the page for the "Enter your knox ID" form, but the URL stays where it
was. A user who logs out on `/chat/<sessionId>` sees the login form at
`/chat/<sessionId>`; the next person to log in on that browser is dropped
straight into that session. The same happens when the 2-hour session expiry
in `UserProvider` fires, and when someone opens a `/chat/<sessionId>` link
without being logged in.

### After

Whenever the gate is ready and has no user, and the current path is not
already `/chat/new`, it navigates to `/chat/new` with `router.replace`.
This covers all three cases with one rule:

- **Log out button** (sidebar account menu → "Log out") on any page.
- **Automatic expiry** (the `setTimeout` in `UserProvider.scheduleExpiry`,
  and the expired-on-load branch in its mount effect).
- **Direct visit** to `/chat/<sessionId>` while logged out.

`replace` is used instead of `push` so the browser Back button does not return
to the old session URL after logout.

Logged-in users are not affected: the effect only runs when `userId` is null.

## A2. `src/components/user-gate.tsx`

Before:


After:

for Next.js 16.3.3.

### A2b. Redirect effect (lines 12–21, inside `UserGate`, right after the `useState`)

Before (lines 10–13):

```tsx
  const { userId, setUserId, isReady } = useUser();
  const [value, setValue] = useState("");

  if (!isReady) return null;
```

After (lines 10–23):

```tsx
  const { userId, setUserId, isReady } = useUser();
  const [value, setValue] = useState("");
  const router = useRouter();
  const pathname = usePathname();
  const loggedOut = isReady && !userId;

  // A logged-out visitor is always shown the login page at /chat/new, so a
  // logout (by button or by expiry) on /chat/<id> does not leave that URL
  // behind for the next login.
  useEffect(() => {
    if (loggedOut && pathname !== "/chat/new") router.replace("/chat/new");
  }, [loggedOut, pathname, router]);

  if (!isReady) return null;
```

Notes on placement:

- The hooks must sit **above** the `if (!isReady) return null;` early return.
  Hooks cannot be called conditionally, so putting them after the return would
  break the rules of hooks and fail lint.
- `isReady` is folded into `loggedOut` so the effect does not fire during the
  first render, before `UserProvider` has read `localStorage`. Without that
  guard a logged-in user opening `/chat/<id>` would be bounced to `/chat/new`
  for one frame.
- The `pathname !== "/chat/new"` check avoids a redundant `replace` when the
  gate is already on the login URL.

The rest of the file (the form JSX and the `return <>{children}</>`) is
unchanged.

# Change B: a loaded session shows only the last reply of each turn

**Files changed:**

| File | Change |
|---|---|
| `src/lib/session-api.ts` | `mapApiSessionDetail`: collapse consecutive assistant messages to the last one. |

---

## B1. Behavior

### Before

Every backend event with a non-thought text part became one bubble. Inside a
single agent turn the model can emit text more than once: a short narration
before a tool call ("only one version exists, proceeding with the search"),
then, after the tool result, the real answer. Both were printed, so a turn
showed two assistant bubbles back to back.

Example session `f6a7ccb8153b46749992c41780f937a0` (user `m.alenova`):

| # | Bubble | Source event |
|---|---|---|
| 1 | user, image + `이 이미지와 유사한 이미지 찾아줘` | `author: user` |
| 2 | assistant, asks for model details | `author: root_orchestrator` |
| 3 | user, `모델은 sidebottom이야 ...` | `author: user` |
| 4 | assistant, one-row version table + "proceeding" | `root_orchestrator`, text part before a `functionCall` |
| 5 | assistant, five-row similar-image table | `root_orchestrator`, final text after the tool result |

### After

Bubble 4 is dropped. Of any run of consecutive assistant messages, only the
last one is kept. User messages are never touched. Result for the example:
bubbles 1, 2, 3, 5.

Rule, on the mapped message list: an assistant message survives only when the
message after it is a user message or there is none.

| Roles in | Roles out |
|---|---|
| user, assistant, user, assistant, assistant | user, assistant, user, assistant |
| user, assistant, assistant, assistant | user, assistant |
| user, assistant, user, assistant | unchanged |
| user, assistant, user (opened mid-run) | unchanged |

## B3. Scope

- **Only session loads.** `mapApiSessionDetail` runs for `getSession`, i.e.
  when a chat is opened from the sidebar or by URL. A reply that arrives from
  a send goes through `/api/chat` and is appended directly, so it is not
  affected.
- **Error bubbles.** A failed turn is mapped to the `ERROR_REPLY` bubble as an
  assistant message, so it takes part in the collapse like any other reply:
  if it is the last assistant message of the turn it is what remains.
- **Session opened mid-run.** If the backend has stored the narration but not
  yet the final answer, the narration is the last assistant message and is
  shown. This was already the case; the final answer shows on the next load.

# Change D: idle logout after 30 minutes

**Files changed:**

| File | Change |
|---|---|
| `src/providers/user-provider.tsx` | Fixed 2-hour expiry becomes a 30-minute idle window that activity pushes forward; tabs stay in sync through the `storage` event; `keepAlive()` added to the context. |
| `src/components/chat/chat-view.tsx` | While a reply is pending, calls `keepAlive()` once a minute so waiting on the agent is not idle time. |

No backend involvement. The login, its expiry and the timers all live in the
browser (`localStorage` + `setTimeout`). The redirect to `/chat/new` on logout
is Change A and needs nothing extra here.

---

## D1. Behavior

### Before

Logging in stored an expiry 2 hours ahead (working tree; 1 hour at `HEAD`)
and armed one timer for it. Nothing moved the expiry; activity was not
tracked. A second tab read the same stored login but ran its own timer.

### After

- **Window.** The login ends after **30 minutes without activity**
  (`IDLE_MS`).
- **Activity** is any `pointerdown`, `pointermove`, `keydown`, `wheel`,
  `scroll` or `touchstart` on the window, or the tab becoming visible again.
  Each one rewrites the stored expiry to now + 30 min and re-arms the timer,
  throttled to once per 15 s (`KEEP_ALIVE_THROTTLE_MS`).
- **Waiting for a reply counts as activity.** While `isSending` is true in
  the chat view (from the send until the reply lands, including the polling
  case), `keepAlive()` is called at once and then every 60 s
  (`PENDING_REPLY_KEEP_ALIVE_MS`). A user who asks a question and then sits
  still is not logged out mid-reply.
- **Multi-tab.** Every write goes to the shared `localStorage` key. Each tab
  listens for the `storage` event: a new expiry written by an active tab
  re-arms the timer in the others; a removal (logout or expiry in any tab)
  logs the others out. One active tab keeps all tabs in; one logout logs all
  tabs out.
- **Background tabs.** Browsers hold back timers in hidden tabs, so
  `keepAlive()` first checks the stored expiry: if it has already passed, the
  call logs out instead of extending. The `visibilitychange` listener makes
  that check run as soon as the tab is shown again.
- **Closed browser.** Unchanged: on load, a stored expiry in the past is
  discarded and the login form shows.

### D2c. Refs and helpers (lines 55–100)

Three refs mirror the stored session for listeners that are registered once
and must not read a stale render: `userIdRef`, `expiresAtRef`,
`lastKeepAliveRef`. `clearUserId` and `scheduleExpiry` are the old functions
wrapped in `useCallback` and also updating the refs. New:

```ts

  localStorage.setItem(STORAGE_KEY, JSON.stringify({ id, expiresAt }));
  userIdRef.current = id;
  setUserIdState(id);
  scheduleExpiry(expiresAt);
}, [scheduleExpiry]);
```

### D2d. `keepAlive` (lines 102–119)

```ts
const keepAlive = useCallback(() => {
  const id = userIdRef.current;
  const expiresAt = expiresAtRef.current;
  if (!id || expiresAt === null) return;

  const now = Date.now();
  if (now >= expiresAt) {        // held-back timer in a hidden tab
    clearUserId();
    return;
  }

  if (now - lastKeepAliveRef.current < KEEP_ALIVE_THROTTLE_MS) return;
  lastKeepAliveRef.current = now;

  writeSession(id, now + IDLE_MS);
}, [clearUserId, writeSession]);
```

### D2e. Mount effect (lines 121–179)

The restore-from-storage block is as before. After it, three listeners are
registered and removed on unmount:

```ts
const onActivity = () => keepAlive();
const onVisibility = () => {
  if (document.visibilityState === "visible") keepAlive();
};
const onStorage = (e: StorageEvent) => {
  if (e.key !== STORAGE_KEY && e.key !== null) return;
  if (!e.newValue) {            // logged out or expired in another tab
    userIdRef.current = null; expiresAtRef.current = null;
    setUserIdState(null); clearTimer();
    return;
  }
  const parsed: StoredSession = JSON.parse(e.newValue);   // activity elsewhere
  userIdRef.current = parsed.id;
  setUserIdState(parsed.id);
  scheduleExpiry(parsed.expiresAt);
};
for (const type of ACTIVITY_EVENTS)
  window.addEventListener(type, onActivity, { passive: true, capture: true });
document.addEventListener("visibilitychange", onVisibility);
window.addEventListener("storage", onStorage);
```

`storage` fires only in *other* tabs, never in the one that wrote, which is
why the writing tab re-arms its own timer inside `writeSession`.
