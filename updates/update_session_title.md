## 1. Why

The frontend assumes the backend names a session by itself after the first
reply. `src/app/api/chat/route.ts` sends `new_session=true` along with the
first `/run` call for that purpose, and the sidebar comment at
`session-sidebar.tsx:132` says the title "generated by the backend after the
first message" shows up through the 5 s poll.

The current backend does not do that on its own. `RunAgentRequest` has only
`query`, so `new_session` is ignored, and naming is an explicit endpoint:

```
POST /apps/users/{user_id}/sessions/{session_id}/title
```

Nothing in the frontend calls it, so a new chat keeps its session id as its
title until it is renamed by hand.

The fix is one call per new chat, made after the first run has finished (with
a reply or with an error) and **before** that reply is put on screen. The
reply is held back until the naming call has settled, whichever way it
settled. Nothing is read from the response: the title is stored in the
session state, which `listSessions()` already reads every 5 s and reports
upward for the sidebar row and the tab title.

---

## 2. Backend contract

| Endpoint | Method | Request | Response model |
|---|---|---|---|
| `/apps/users/{user_id}/sessions/{session_id}/title` | `POST` | none (path only) | `CreateSessionTitleResponse { session_title: str }` |

Status codes: 200 on success, 400 when the runner raises `ValueError` (for
example an unknown session), 500 on anything else.

Requirement on the backend: the generated title must be written to
`state.session_title`, because that is the only place the frontend reads
titles from (`mapApiSession` and `mapApiSessionDetail` in `session-api.ts`,
and the `PATCH .../title?session_title=` rename writes there too).

The proxy at `src/app/backend/[...path]/route.ts` forwards every method and
path under `/backend`, so the new URL needs no proxy change.

## 3. Behavior after the change

Sending the first message of a new chat, in `handleSend`:

1. `POST .../sessions` creates the session. Unchanged.
2. `POST /api/chat` runs the agent, as today. Unchanged. The spinner and
   "Thinking..." are up, the box is locked.
3. The run settles, with a reply or with an error. The reply (or the
   "Sorry..." line) is built but **not yet shown**.
4. Only when the session was created in this call:
   `POST .../sessions/{id}/title` is sent and **awaited**. Its body is
   ignored. A non-2xx status or a network failure is logged to the console
   and otherwise ignored. The spinner stays up throughout.
5. The reply (or the error line) is put on screen. A real reply starts its
   typing reveal at this point. The spinner goes away, the box unlocks.
6. Within at most 5 s the sidebar poll reads the new title from
   `state.session_title`. The existing `onCurrentSessionTitleChange` wiring
   (`session-sidebar.tsx:135-141` to `chat-view.tsx:551`) updates the tab
   title, and the sidebar row updates with it. No new UI code.

Consequences worth knowing:

- **Latency.** The first reply of every new chat appears later by however
  long the title call takes. If the backend generates the title with a model
  call, that is typically a second or more. The user sees "Thinking..." for
  that time, which is the intended signal.
- **Failure of the title call never costs the reply.** The call is wrapped so
  it cannot throw. In particular, a title failure after a successful run must
  not drop into the `catch` that prints the "Sorry..." line; that is why the
  wrapper, not the raw `SessionStorage` call, is awaited.
- **Both outcomes of the run name the chat.** The await sits in the `try`
  (reply received) and in the `catch` (run failed), so a chat whose first run
  failed is still named, and its error line waits for that too.

The call is **not** made when:

- the message goes to an existing session (`isNewSession` is false);
- creating the session failed. That `catch` returns before the run is
  attempted (line 454), so neither branch below is reached.

```ts
    userId: string,
    sessionId: string,
    title: string,
  ): Promise<void> {

    const res = await fetch(
      `${API_BASE}/apps/users/${encodeURIComponent(
        userId,
      )}/sessions/${encodeURIComponent(sessionId)}/title?${params.toString()}`,
      {
        method: "PATCH",
        headers: {
          Accept: "application/json",
        },
      },
    );

    if (!res.ok) {
      throw new Error(`Failed to rename session: ${res.status}`);
    }
  }
```

```ts
  /**
   * Asks the backend to name the session after its first exchange. Called once
   * per new chat, after the first run has finished. The title is stored in the
   * session state, where listSessions() and getSession() read it from, so the
   * sidebar's poll picks it up on its own; the response body is not needed for

    userId: string,
    sessionId: string,

      `${API_BASE}/apps/users/${encodeURIComponent(
        userId,
      )}/sessions/${encodeURIComponent(sessionId)}/title`,
      {
        method: "POST",
        headers: {
          Accept: "application/json",
        },
      },

      throw new Error(`Failed to create session title: ${res.status}`);
    }
```

## 7. Not part of this change

- **`new_session` on the run call.** `chat-view.tsx:481-483` appends
  `newSession=true` to the form, and `src/app/api/chat/route.ts:37-39` and
  `:78-81` forward it to `/run` as `new_session`. The backend's
  `RunAgentRequest` has no such field, so it is ignored. Harmless; can be
  removed in a later cleanup, together with the `isNewSession` plumbing in the
  route. The `isNewSession` flag in `chat-view.tsx` itself stays, since the
  new calls depend on it.
- **Using the response.** Since the call is awaited anyway, the generated
  title could be applied straight away instead of waiting up to 5 s for the
  poll: have `createSessionTitle` return `data.session_title`, have
  `nameNewSession` return it (or `null` on failure), and call
  `setCurrentSessionTitle(title)` when it is non-null. Left out on purpose;
  the request is to ignore the result.
- **Server-side alternative.** The call could be made from
  `src/app/api/chat/route.ts` after the `/run` response, before replying to
  the browser. That would also hold the reply back, but a failure of the
  route itself (500, or the Next server unreachable) would skip the naming,
  and the route would have to be told the session is new. The client already
  knows, and its `catch` covers that case, so the client is the better place.
- **Sidebar comment** at `session-sidebar.tsx:132-134` still reads as if the
  backend names the session on its own. Still true in effect after this
  change; reword only if it bothers you.

## 8. How to verify

Type-check first; it must be clean:

```
npx tsc --noEmit -p tsconfig.json
```

With the backend running and the network panel open:

1. Start a new chat and send a message. Expect, in order:
   `POST .../sessions`, `POST /api/chat`, then `POST .../sessions/{id}/title`.
   "Thinking..." stays up until the title request has completed; only then
   does the reply appear and start typing out. Within 5 s the sidebar row and
   the tab title change from the session id to the generated title.
2. Throttle or breakpoint the title endpoint so it takes several seconds. The
   reply must not appear before it returns, and the box stays locked.
3. Send a second message in the same chat. No `POST .../title`, and the reply
   appears as soon as `/api/chat` returns.
4. Open an existing chat and send a message. No `POST .../title`.
5. Make the first run fail (for example stop the backend between creating
   the session and sending, or send something the agent rejects). The
   `POST .../title` is still sent, and the "Sorry, I encountered an error"
   bubble appears only after it has returned.
6. Make only the title call fail (backend returns 400 or 500 for it, or kill
   the backend after `/api/chat` returned). The real reply still appears,
   after the failed call returns; the console shows one
   `Error creating session title:` line; the sidebar keeps showing the
   session id as the title.
